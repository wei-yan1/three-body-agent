# StoryRole 深度回答策略设计

本文只定义深度回答内部的三项策略：Plan、ReAct、Agent 互查的适用条件；Token、耗时和模型调用预算；情感类、事实类、关系类问题的执行方式。

Laya 已经负责本轮问题分类和能力判断。`quick`、`deep` 是用户可见的回答模式，下面的策略只在 `deep` 模式内部生效，不新增第三种用户模式，也不替代 Laya。

## 1. Plan、ReAct、Agent 互查的适用条件

### 1.1 Plan

Plan 是深度回答的默认内部结构。它的作用是把 Laya 已经识别出的意图转成有限的分析任务和证据要求，而不是再次判断问题类型。

Plan 适用于：

- 需要同时使用人物画像、小说原文、关系状态或时间线的提问。
- 需要区分原文事实、角色动机和模型推断的提问。
- 需要多个检索子问题才能回答的提问。
- 用户明确要求“分析、比较、解释原因、结合原文”的提问。

Plan 不负责：

- 重新判断用户属于哪类问题。
- 自由决定无限数量的 Agent 调用。
- 输出模型内部思维链。
- 直接生成最终回答。

Plan 的最小结构：

```json
{
  "claims_to_resolve": ["需要回答的核心命题"],
  "evidence_requirements": ["每个命题需要什么证据"],
  "search_queries": ["最多三个检索问题"],
  "answer_shape": "角色立场 + 依据 + 不确定性",
  "max_followup_searches": 0
}
```

硬限制：核心命题最多 3 个，初始检索问题最多 3 个，补充检索最多 1 轮。

### 1.2 ReAct

不采用开放式 ReAct。开放式 ReAct 会让模型自行循环调用工具，难以控制延迟和费用。

采用受限 ReAct，只在下列条件同时满足时启用：

1. Laya 判断本轮需要深度回答。
2. 初始证据不足、相互矛盾，或无法覆盖 Plan 中的核心命题。
3. 还有剩余时间和费用预算。

受限 ReAct 流程：

```text
初始 Plan
→ 初始检索
→ 证据充分性检查
→ 必要时生成最多两个补充查询
→ 再检索一次
→ 结束
```

禁止事项：

- 不允许超过 1 次补充检索。
- 不允许因为模型“想继续思考”而循环。
- 不允许联网结果绕过当前角色时期和时间线约束。
- 不允许把未验证的网页内容直接当作小说事实。

如果补充检索超时，直接使用已有证据，并在回答内部降低确定性，不阻塞用户。

### 1.3 Agent 互查

Agent 互查用于检查结论，不用于让多个 Agent 自由讨论。

推荐分工：

```text
Evidence Analyst
  输出事实、观察、推断和不确定性

Role Cognition
  输出角色立场、情绪姿态、回答重点

Consistency Guard
  检查证据支持、时期边界和人设一致性
```

互查适用于：

- 人物动机和价值冲突。
- 人物前后变化。
- 关系判断。
- 涉及未来、结局或时间线边界。
- 情感问题中容易出现过度承诺或人格漂移的回答。

互查不适用于：

- 简单事实问题。
- 原文中有明确答案的问题。
- 普通情绪陪伴。
- 证据为空的情况。没有证据时增加审查 Agent 只会增加成本，不能提高可靠性。

## 2. Token、耗时和模型调用预算

### 2.1 深度模式预算

| 阶段 | 默认上限 | 说明 |
|---|---:|---|
| Laya 分类 | 由现有路由预算控制 | 不属于 Deep 内部重复调用 |
| Deep Plan | 1 次模型调用 | 仅生成命题、证据要求和检索任务 |
| 初始检索 | 最多 3 个查询 | 向量、BM25 和 Rerank 不等于额外 LLM 调用 |
| Evidence Analyst | 1 次模型调用 | 归纳证据，不生成最终回答 |
| Role Cognition | 1 次模型调用 | 决定角色立场和回答姿态 |
| Answer | 1 次模型调用 | 生成最终回答 |
| Consistency Guard | 默认规则检查；高风险时最多 1 次模型调用 | 只做最小修正 |
| ReAct 补充检索 | 最多 1 轮、最多 2 查询 | 仅证据不足或冲突时执行 |

默认目标：Deep 一般不超过 4 次模型调用；高风险且需要补充检索时不超过 5 次。超过预算时跳过补充环节，不跳过最终回答。

### 2.2 时间预算

目标不是让每个节点都跑满超时，而是保证用户可预期：

| 路径 | 目标耗时 | 绝对上限 |
|---|---:|---:|
| Deep 无补充检索 | 8 秒 | 25 秒 |
| Deep 有补充检索 | 12 秒 | 30 秒 |
| Deep + 联网 | 10 秒 | 30 秒 |

可以并行的工作：

- 用户记忆召回
- 关系状态读取
- 时间线检查
- 本地检索和 Tavily 检索

不能并行的工作：

- 证据分析必须在初始检索后执行。
- 角色认知必须看到证据分析结果。
- 最终回答必须看到上下文和角色认知结果。

## 3. 不同问题类型的执行方式

Laya 已经输出问题类型。Deep 只读取该类型并选择对应的内部执行路径。

### 3.1 情感类问题

典型问题：

- “你还在乎我吗？”
- “我很难过，你会怎么安慰我？”
- “你是不是已经不想理我了？”

目标是保持情感回应自然，同时避免角色人格漂移和不负责任的绝对承诺。

执行方式：

```text
关系状态
→ 用户记忆
→ 当前对话历史
→ 人物画像中的情绪和关系边界
→ Role Cognition
→ 回答
```

默认不做多路小说检索。只有问题涉及具体剧情事实、人物过去行为或关系变化时，才加入原文检索。

情感类问题通常不需要开放式 ReAct。只有出现关系状态冲突，或用户要求结合原文判断时，才启用一次受限补充检索。

回答重点：

- 先回应用户表达的情绪。
- 再以当前角色的立场回应。
- 不把角色回应说成现实承诺。
- 不为了安慰用户让角色违背画像和时期边界。

推荐预算：2 至 3 次模型调用，目标 6 秒内完成。

### 3.2 事实类问题

典型问题：

- “这件事发生在哪一章？”
- “这个角色当时知道什么？”
- “原文中他为什么离开？”

执行方式：

```text
Plan
→ 本地向量检索 + BM25
→ 时间线过滤
→ 必要时 Rerank
→ Evidence Analyst
→ Answer
```

事实类问题优先使用小说原文，用户记忆和关系状态只作为辅助。回答必须区分：

- 原文明确写出的事实。
- 根据多段原文归纳出的结论。
- 目前证据无法确认的部分。

如果原文证据已经充分，不启用 ReAct，也不调用 Role Cognition。只有事实冲突或检索为空时，才允许一次补充检索。

推荐预算：2 至 3 次模型调用，目标 8 秒内完成。

### 3.3 关系类问题

典型问题：

- “他怎么看待这个人？”
- “我们现在是什么关系？”
- “他为什么信任或不信任我？”

执行方式：

```text
关系状态
→ 用户记忆
→ 相关原文和关系证据
→ Evidence Analyst
→ Role Cognition
→ Answer
```

关系类问题比一般情感问题更需要证据，因为它可能要求解释人物关系变化。应优先读取关系状态，再根据需要检索原文，不应只靠向量相似度直接判断关系。

如果关系状态和原文证据冲突：

1. 以原文事实约束关系判断。
2. 标记关系状态需要更新。
3. 回答中保留不确定性。
4. 不在当前回答中直接永久修改关系状态，交给关系更新流程处理。

推荐预算：3 至 4 次模型调用，目标 10 秒内完成；涉及未来或结局时才增加时间线检查和 Guard。

## 总结

```text
Laya：分类和能力判断
Deep：选择更完整的内部执行路径
Plan：规定需要解决的命题和证据
ReAct：证据不足时最多补充一次
Agent 互查：只在高风险或复杂推断时启用
```

Deep 的核心不是增加 Agent 数量，而是在固定预算内让回答更有依据、更符合角色、更少浪费调用。
